6 Configure Pricing

The condition technique, pricing procedures, procedure determination, exclusion groups, and pricing limits.

The Single Largest Configuration Technique in SD

"Of the many possible prices for this product, which one does SAP actually use?"

The condition technique is how SAP chooses between competing alternatives — a list price, a customer-specific price, a material discount — based on the conditions of the sale (who's buying, what they're buying, which sales area). It isn't only used for pricing: text determination, output determination, material determination, and account determination all reuse the exact same mechanism.

The Condition Technique Chain

1
Field Catalog: the pool of fields (customer, material, sales org...) available to build condition tables from.
2
Condition Table: a specific combination of fields (e.g. SalesOrg + Customer + Material) that a condition record can be stored against.
3
Access Sequence: the tables to search, in order, most-specific to most-general.
4
Condition Type: the pricing element (price, discount, surcharge, tax) that owns one access sequence.
5
Pricing Procedure: the ordered list of condition types that produces the final net/total value.

The result of walking this chain is a condition record — the actual stored value (e.g. "$450 for Customer 1000 / Material X").

The 9-Step Customizing Sequence

Build the condition technique bottom-up — every later step depends on the one before it.

1 Add any missing fields to the field catalog.
2 Create the condition tables you need [V/05].
3 Create the access sequence [V/07].
4 Assign the condition tables to it, most-specific first.
5 Create the condition type [V/06].
6 Assign the access sequence to the condition type.
7 Add the condition type to a pricing procedure [V/08].
8 Set up pricing procedure determination (CuPP + DoPP + sales area).
9 Create the condition records [VK11] — nothing prices until this happens.

Access Sequence Example: Z007

Most-specific table first, most-general last. The system stops at the first hit.

10 · Table 909 SalesOrg + PriceGroup + Material
not found, try next
20 · Table 004 Material only

The exclusive indicator on a step stops the search once a record is found — set it to avoid wasted table reads and, when using exclusion groups, unset it so every candidate gets a chance to be compared.

Pricing Procedure Determination

Which pricing procedure a document uses is never hardcoded — it's determined from three inputs:

Sales Area SOrg+DChl+Div
Customer Pricing Proc. (CuPP) [OVKP], on cust. master
Document Pricing Proc. (DoPP) [OVKJ]/[OVTP], on doc type
Pricing Procedure e.g. RVAA01

A billing document can use a different DoPP than the sales order that created it — useful when order and invoice pricing structures diverge.

Anatomy of a Pricing Procedure (V/08)

Every column controls a distinct piece of behavior — this is the reference sheet for what each one does.

Step / Cntr

Sequence number; Cntr allows multiple condition types at one step (e.g. three freight surcharges all at step 100).

CTyp

The condition type — the backbone linking to the access sequence and condition record.

From / To

Either the step range a subtotal sums, or the base step a % condition calculates from.

Man / Mdt

Man = entered manually only; Mdt = mandatory, missing it blocks the document (e.g. delivery can't be created).

Stat

Statistical — the value is shown but excluded from the Net Value total (e.g. VPRS cost).

SubTo

Writes the running value into a subtotal field (A = credit price/KOMP-CMPRE, B = cost price, 4 = freight...) used downstream by credit checks, LIS, etc.

Reqt

A requirement routine that must return true before this step is even accessed — the highest-leverage performance lever in the whole procedure.

AltCTy / AltCBV

Alternative calculation type / base value formulas — override the standard condition technique math for a step (e.g. profit margin = net value − cost).

ActKy / Accrls

Account key(s) routing the value to a GL account in FI — this is the pricing-to-accounting bridge.

A condition type of class B (price) allows only one active price per item — a second price-class condition type finding a value invalidates every price found before it in the procedure.

Condition Exclusion Groups

Stops a customer from stacking every applicable discount by keeping only the best (or worst) one active.

Item priced at $100 — two discounts compete:
K007 — 50% off−$50
K005 — flat discount−$45 (inactive)
Result: K007 winsBest for customer

Drop the price to $90 and K007's 10% becomes only $9 — K005's flat $10 would then win instead. Exclusion groups re-evaluate per document, not statically.

Required setup: exclusion group [V/32] → assign condition types → assign the group to the pricing procedure. Using "best within a type" instead of "best across types" also requires turning off the exclusive indicator on that type's access sequence, or the system stops at the first hit before it can compare.

Pricing Limits

Any condition type editable in the sales order can be abused — a limit caps how far a rep can push it.

Example: discount Z100 capped at 100%

Without an upper limit, an unchecked 100%+ manual discount can push net value negative — effectively handing the customer a credit note through a sales order.

Set via [OVB2]. Prefer percentage-based limits for discounts (they scale with quantity); use value-based limits for flat caps like a maximum freight surcharge.

Also gate pricing at the item category level — [VOV7] style config for pricing/statistics relevance, and separately activate cost determination so a condition type like VPRS actually resolves from the material's standard/moving-average price.

Price-Relevant Master Data Fields

Three fields exist purely to give pricing something coarser than "one customer, one material" to key off:

Customer Price List Type

Groups customers who share a resale price list (e.g. "Wholesale" vs "Retail"). Lives on the customer master sales view.

Customer Pricing Group

A freer-form segmentation of customers for discounting (e.g. "Key Account"). Also on the customer master.

Material Group

Groups materials for pricing purposes. Set on the material master's Sales Org 2 view.

A condition supplement attaches automatically whenever its "parent" condition is found — e.g. every time a material's PR00 price is determined, an associated discount rides along without a separate access.

Top Certification & Project Takeaways for Pricing

Must Know
The chain is fixed: Field Catalog → Condition Table → Access Sequence → Condition Type → Pricing Procedure → Condition Record.
Never edit standard objects: copy to a Z-prefixed key and modify the copy.
Procedure determination = Sales Area + CuPP + DoPP. No pricing procedure is ever hardcoded to a document type alone.
Requirements are the #1 performance lever — placing one at the pricing procedure step avoids reading the access sequence, tables, and fields entirely when it isn't needed.
Pricing type G ("copy pricing elements unchanged and redetermine taxes") governs what re-prices when a document is copied — a classic interview question.
Exclusion groups prevent discount stacking — always set them up wherever more than one discount could legitimately apply to the same item.
